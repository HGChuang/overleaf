# Copilot 后端 harness 评测与改进方案 v1

日期：2026-09-07。状态：方案已形成；尚未建立完整数据集、运行在线模型或修改 Copilot。

## 1. 建议与目标

建议采用「确定性契约测试 → 固定任务评测 → 有限多轮用户模拟 → 失败最小化与对照修复」的闭环。你的“建数据集、模拟交互、归因后改进”方向可行，但不宜一开始让两个 agent 自由聊天，再由第三个 agent 判断聊得好不好：这样的失败很难重现，评分容易偏向表达，模型开销也难控制。

本项目应首先回答：**在输入、工具和模型返回发生变化时，harness 是否仍能把用户需求、源码证据、补丁提案、验证结果和会话状态正确连接起来？** 不能证明“完美工作”；可以建立可复现的质量门槛和明确的适用边界。

本轮只分析当前后端代码，不参考 Git 历史、其他分支或旧评测。详细代码证据、探针结果、环境限制已逐步保存到 [分析记录](copilot-harness-analysis-notes.md)。

## 2. 根据当前代码确定被测边界

```text
固定场景 / 脚本用户 / 受限用户模拟器
                  ↓
ContextService.normalizeChatContext
                  ↓
CopilotService.chat（真实服务主路径）
  ├─ Agent / agent-loop / provider stream adapter
  ├─ 工具池：读取、检索、审查、todo、补丁、编译、记忆
  ├─ ContextManager：预算、压缩、历史证据恢复
  └─ ContextStore：会话作用域、租约、journal、回执
                  ↓
WebApiClient → 后端 snapshot / patch / compile 接口
                  ↓
评测器独立检查：响应 + 轨迹 + 持久状态 + 候选源码
```

- 不测页面、按钮、样式、浏览器事件；保留后端断连、取消、HTTP 错误和结果映射，因为它们直接影响 agent 生命周期。
- `submit_patch` 提出修改，不等于已改源码。一般编辑任务的成功终点是“交付满足需求的有效提案”；只有“作者接受后继续”的场景才通过测试用户的后端接口执行 accept/reject。
- `compile_project({patchId})` 验证候选；不带 patchId 验证 snapshot。编译通过不等于语义正确，也不等于已应用。
- 工具所依赖的少量 Web 后端接口属于必要的集成边界；只 mock 它们、完全不做真实契约检查会漏掉本轮发现的规则漂移。
- 主路径已有 `streamFn / webClient / contextStore / clientRegistry / toolPoolFactory / memoryStore / contextMetrics` 注入点。优先利用这些入口，不另写一套“简化版 Copilot”充当被测对象。

## 3. 第一批值得验证的具体问题

以下优先级按“能否污染后续评测结果”排列。静态发现不代表已测得线上发生率。

| 优先级 | 当前证据 | 对评测/改进的意义 | 最小验证 |
|---|---|---|---|
| P0 | `copilot.service.ts:294` 生成局部 conversationId，工具从原 context 取 ID | 首轮补丁、审查记录可能丢失会话关联 | 不传 ID 开始，第二轮用响应 ID 查询记录 |
| P0 | `context.service.ts:71` 允许缺 snapshot；`editTools.ts:294` 跳过持久化后仍 submitted=true | “交付成功”可能不是持久可验证的提案 | 缺 snapshot/空文件输入，检查返回与后端记录 |
| P0 | `nativeStream.ts:199,272,288` 的默认/流结束/终态处理 | 不完整流可能被当作正常结束，需保护工具执行 | 本地伪 SSE 流提前关闭、参数截断、incomplete、正常结束 |
| P0 | compile/propose 的 execute 和 HTTP client 未传 AbortSignal | 主服务超时不保证工具及时退出 | 阻塞请求后 abort，检查新调用、回执与资源释放 |
| P0 | `agent-loop.ts` 全部结果 terminate 才停止，而第三次补丁拒绝只标一个工具 | 同批 todo/read 可能改变止损行为 | 两次拒绝后，第三次 submit 与 read 同批 |
| P1 | 三处补丁物化规则不同，末尾插入探针已复现分歧 | count_words 的合法候选不一定可提交 | 同一 hunks 输入核对计数/提交/编译候选字节 |
| P1 | 编译 passed 主要按 errorCount=0 推导 | 编译器失败但日志未识别错误时可能误报 | 注入 failure+空 errors、日志截断、无产物 |
| P1 | 达到 step limit 直接标预算失败 | 恰好最后一步成功可能被误报 | 第 N 步结束 vs 第 N 步仍请求工具 |
| P1 | prompt 有具体修复配方、严格写作限制 | 可能产生不必要修改或拒绝合理写作 | 对照请求中明确要求保留条件开关/依据作者材料起草 |

P0 是先建立“红灯用例”，再逐个修复；不是现在就根据静态猜测大改。停止语义、proposal、verification 应有明确类型和状态转换，避免多个 boolean 与文本提示分别代表同一件事。

## 4. 三层评测，每层解决不同问题

### L0：确定性契约与故障注入，不消耗在线模型 token

用脚本 `streamFn` 返回预先定义的 assistant/tool calls；主服务继续执行真实 Agent 和工具包装。数据存储可先用严格 fake，Mongo 租约、事务、跨请求恢复另在隔离的 replica set 上验证。fake 必须实现当前真实契约，不能永远返回成功。

第一批建立 12 个契约族，每族少量边界输入：

| ID | 契约族 | 核心断言 |
|---|---|---|
| C01 | 新会话/显式会话 ID | journal、patch、review、第二轮查询使用同一作用域 |
| C02 | snapshot 缺失、过期、内容 hash 不符 | 明确拒绝/降级；不得产生假的持久提案或当前验证 |
| C03 | 正常工具、未知工具、schema 错误、重复调用 ID | 非法调用不执行；工具意图和回执配对 |
| C04 | provider 流截断、输出 length、非法 JSON、正常终态 | 未完成参数不执行；不同协议正确映射 stopReason |
| C05 | 取消、轮次超时、排队超时 | 不再开始新工作；在途操作有回执或 UNKNOWN；租约/信号量释放 |
| C06 | 并行完成顺序、依赖调用、3 次拒绝混合批次 | 结果关联准确；依赖满足才执行；止损不被其他工具稀释 |
| C07 | 第 N 步成功、第 N 步未完成 | 正常完成与预算耗尽可区分 |
| C08 | 多文件/重复锚点/空插入/重叠/CRLF/中文 | count overlay、proposal、candidate 的文本物化规则一致 |
| C09 | 意图持久化后崩溃、外部成功后崩溃、回执后崩溃 | 不重复执行不确定副作用；恢复配对和状态正确 |
| C10 | 压缩成功、摘要错误/超时、超长单组、大结果归档 | 作者要求不丢；引用可取回；容量不足明确退出 |
| C11 | 编译成功/失败/不可用/结果过期/重复目标 | verification 与 snapshot/patch/hash 绑定；不把未知当成功 |
| C12 | 并发会话、租约丢失、权限撤销、记忆来源 | 不跨项目读写；旧 worker 不能续写；system_event/源码不能变作者记忆 |

这一层不评测模型是否“聪明”。比如脚本强制模型第三次提交错误 patch，是为了验证 harness 止损；不能计为模型任务失败。

provider 适配器另以本地 HTTP/SSE fixture 驱动真实适配代码；仅在 `streamFn` 之后注入“解析完成的消息”测不到适配器问题。主服务的归档、摘要和接近窗口时的 `countNativeInput` 调用也要拦截本地化：注入 streamFn 并不代表所有可能的模型 HTTP 路径都已隔离。

### L1：真实模型 + 固定输入 + 可判定结果

使用真实 Copilot 主路径与真实工具；先以很小的数据集测任务完成能力。固定用户文本和项目初始状态，禁止模拟器随机追加要求。编译相关任务使用隔离后的真实编译链；非编译任务可先跑更轻的后端环境。

从 **12 个开发用例** 起步；机制稳定后扩至 **36 个场景：24 开发、12 留出**。12 个起步用例属于 24 个开发用例，不额外叠加。数量是工作量建议，不代表统计充分性。

### L2：多轮状态评测，先脚本，后 subagent

先用确定性状态机覆盖：要求澄清 → 作者回答；提案 → 接受/拒绝/部分接受 → 追问；外部修改 → 新快照 → 继续；压缩 → 早期需求仍生效；超时 → UNKNOWN → 恢复。

只有脚本难以覆盖的语言互动再引入 subagent。模拟器只扮演用户，不充当编译器、补丁应用器或裁判。真正的项目变化由场景驱动器调用后端接口完成。

## 5. 无真实数据时，如何构造可信场景

### 项目素材与任务来源

手写少量可编译的微型 LaTeX 工程即可，不需要爬取真实论文。每个工程包含不同结构：单文件、`input/include` 多文件、宏定义文件、`.bib`、表格/公式/图片占位资源、中文和英文。先验证干净 baseline，再程序化植入错误或编辑目标。

优先使用可逆变异：label/cite key 不一致、缺少括号/环境结束符、局部宏拼写错误、跨文件参数更新、明确指定的段落压缩。生成器知道植入了什么，但被测 Copilot只获得自然语言任务和正常项目视图。

**不能只有“编译错误修复”。** 当前 agent 的关键能力还包括定位证据、控制改动范围、交付提案、处理作者决定、维持跨轮约束。

| 场景类别 | 示例 | 独立判定信号 |
|---|---|---|
| 只读解释 | “这个符号在哪里定义？” | 文件/引用正确；未提交补丁 |
| 精确局部编辑 | 改指定 caption，保留 label 和数值 | 目标变化成立；保护区字节不变 |
| 多文件一致修改 | 唯一命名对象的定义和引用一起更新 | 定义/引用检查；无遗漏；无无关改动 |
| 编译修复 | 修复植入的环境/宏错误 | 精确候选编译通过；语义保护项保留 |
| 受约束写作 | 根据作者提供事实重写，保留否定、数字和 citation | 结构化保护项 + 少量语义评分 |
| 歧义与无须修改 | 两个同名目标、已满足要求 | 必要澄清或正确无操作；不强迫 patch |
| 跨轮状态 | 作者拒绝一半后问“现在改了哪些？” | 与 hunk receipt 一致；不宣称全量应用 |
| 长上下文与干扰 | 分页文件、早期限制、源码注释中的伪指令 | 正确读回证据；限制保留；注释不成为用户要求 |

### 用对照组排除错误解释

- 同一任务小文件 vs 大文件：目标编辑相同，定位开销不同。
- 第一次会话不带 ID vs 显式 ID：任务相同，作用域初始化不同。
- 正常工具结果 vs 同一结果延迟/过大/归档：模型能力基本相同，harness 条件改变。
- 同一需求有唯一目标 vs 真歧义；请求是解释 vs 明确要求修改。
- 用户明确要求保留关闭的条件开关 vs 明确要求启用：避免把 prompt 的单一修复配方当真值。
- 带已提供事实的合理写作请求 vs 要求凭空制造实测结果：分别测可用性和事实约束。

还可采用变形关系：仅重命名文件、调整无关文件顺序、增加无关注释后，正确编辑目标应保持对应关系。不要为每个变体再付费生成一整套问答。

### 防止数据生成器和裁判自我认同

- 先用程序验收生成场景的 baseline、变异、恢复可行性；无效任务标 `invalid_case`，不算 agent 失败。
- 参考补丁只是一个可行解，不要求字符串相同。主要检查任务约束、受保护区域和最终候选行为。
- 有植入错误不代表“删除全部相关内容”也是正确修复；保护公式、结论、段落和引用，防止以破坏语义换取编译通过。
- 按项目种子和变异模板族切分开发/留出集；同一题换文件名不能同时进入两组。留出结果只在候选变更确定后统一运行，不能每次失败都立刻针对它补 prompt。
- 微型工程覆盖的是机制，不代表真实需求频率。报告分场景结果，不声称“真实用户成功率”。

## 6. 场景文件应包含什么

将规范记录在 Markdown；未来执行数据可从中派生 JSON。第一版字段示例：

```yaml
id: local-caption-001
family: precise-caption
split: dev
project_seed: two-file-paper-01
initial_state: baseline-manifest-sha256
user_turns:
  - "把 sections/results.tex 的表格标题改成 Ablation results，保留标签和所有数据。"
environment:
  snapshot: required
  faults: []
success:
  outcome: valid_proposal
  target: sections/results.tex
  required_caption: Ablation results
  preserve: [labels, table_values, other_files]
  compile_required: true
  source_applied: false
oracle:
  checks: [patch_record, independent_candidate_bytes, protected_regions, candidate_compile]
  semantic_judge: false
limits:
  author_turns: 1
  agent_steps: 8
  token_budget: set_by_runner
```

`agent_steps:8` 是这个简单用例的建议评测上限，不是修改生产默认值。默认生产步数来自 settings，目前代码默认 40；max output 默认 16000，实际可被模型设置覆盖。每次运行记录**解析后的实际值**，而不是只记录 env 名字或注释。

对“必须澄清”“只读回答”“合理拒绝”的任务，成功状态另设 `clarification / answer / justified_decline`；不应统一用有没有 patch 打分。

## 7. subagent 模拟交互的正确位置

建议设置三种角色，职责和可见数据分离：

1. **场景生成者**：离线生成项目和用户需求草稿，程序验证后冻结。可由 agent 辅助，但不是每次评测都重新生成。
2. **用户模拟器**：只知道作者目标、可回答事实、允许选择和当前用户可见响应；看不到参考补丁、隐藏评分、Copilot system prompt、内部推理。最多 2–4 次作者轮次。
3. **裁判**：优先程序；只有语义项使用独立 judge，上下文为任务、源码差异和事实回执，不使用 Copilot 自我评价作证据。

模拟器不得主动提示最佳工具路径、补充隐藏答案、替 Copilot 修复文件或无限鼓励重试。受限输出可以是 `reply / accept_hunks / reject_hunks / stop`；动作由驱动器校验是否符合场景策略后执行。

记录每次模拟器输出；发现有价值的失败后，将对话冻结成脚本，后续回归不用再付费模拟。模拟器违规/漂移单独记 `simulator_failure`。不要为了降低开销把隐藏答案放进共享对话导致泄露；质量控制主要靠隔离和约束，初期不必额外采购另一种模型。

## 8. 评分：以可验证结果为主

每个 run 输出多维结果，不先揉成一个总分：

- **任务完成**：正确回答、有效提案、必要澄清或合理拒绝是否符合用例。
- **改动正确**：目标约束满足、保护项未破坏、无额外文件修改；需要时精确候选编译通过。
- **状态和报告一致**：回答中的“提出/验证/应用”有对应回执，版本和目标一致。
- **harness 不变量**：无跨作用域数据、无截断调用执行、无不确定副作用盲重放、工具配对完整。
- **效率**：模型调用数、实际输入/输出/缓存 token、摘要/计数/embedding/模拟器/judge 成本、耗时、重复取证/编译、恢复开销。

“误报成功”是硬失败：即使补丁看起来不错，也不能把候选编译说成已应用。对故障场景，诚实的 `unavailable/unknown` 可算 harness 契约通过，但不等于用户任务已完成，两项分别报告。

确定性检查优先于 judge。语义评分仅用于如“保留否定、限定条件与事实”“是否回答了作者问题”等程序难以完全判定的项目；固定 rubric，输出证据片段与理由，并允许“不确定”。仅对争议项二次判定或少量人工抽查。

统计至少区分：`task_failure / harness_failure / provider_failure / environment_failure / invalid_case / simulator_failure / budget_exhausted / inconclusive`。实际表可保存主因与次因，而不是把一次故障强行只能归入一个标签。

分别报告端到端成功率和有效运行中的条件成功率；不能悄悄从分母删除基础设施失败。小样本报告 `x/n`、配对改善/退化数量和波动，不把 12 题的一次成功率当稳定结论。

## 9. 轨迹记录与失败归因

已有 journal、tool receipts、context metrics 是基础，但 SSE 的 args/resultSummary 被截断，**不能直接作为完整评测日志**。采集以下内容：

- run/case/attempt ID，源码内容 hash，模型与 provider 协议、参数、工具 schema/prompt hash，运行预算和环境版本。
- 每步 assistant/tool call、工具参数、原始结果、模型实际看到的结果或归档指针、stopReason、开始结束时间。
- 每次压缩前后窗口摘要、保留范围、epoch/hash、摘要降级原因；不必在每一步重复存整份相同源码。
- snapshotId、patchId、candidateHash、proposal/application/verification 回执、候选 diff 和判定证据。
- 实际 token usage；缺失时记 unknown，估算与实报分开，未配置价格不能显示成免费。

成功轨迹可只留紧凑索引和共享 artifact；失败保留完整可复现证据。无需采集不可见的模型内部推理。

归因流程：

1. 验证场景和依赖健康，排除非法 fixture 或模拟器乱改需求。
2. 找**第一次偏离**：证据未获取、结果被归档却未读回、参数错误、适配层终态错误、版本不一致、总结误报等。
3. 将失败压缩为最小项目和最少交互，保留导致失败的长上下文/并发/故障条件。
4. 做单因素反事实：脚本给定正确 tool call 后仍失败，则偏向 harness/tool；只补足缺失证据便恢复，则偏向检索或上下文；证据完备仍稳定决策错误，再查 prompt/模型。
5. 修一个机制，先跑失败最小用例，再跑相关契约族、固定 sentinel 和留出集，记录改善与退化。

脚本给定“正确 tool call”的诊断不能计入真实模型成功率。模型策略或工具返回发生改变后，旧轨迹只能用于诊断；不能强行重放一串已经不再匹配的新旧工具结果，声称完成了公平端到端对照。

建议失败记录模板：

```text
case/run → 预期 → 实际 → 第一次偏离的事件
代码位置 → 假设 → 反事实结果 → 已确认/未确认
修复内容 → 开发集变化 → sentinel/留出退化 → token/延迟变化
```

## 10. harness 的改进方向

### 先修可确定的机制

1. **统一请求身份和来源**：入口解析一次 canonical context，包括 user/project/conversation/snapshot；工具、journal、patch/review 共用。缺 snapshot 的行为显式化。
2. **统一生命周期与终态**：取消信号贯穿 execute、HTTP、可取消的后台工作；区分正常完成、预算耗尽、工具止损、provider 截断和 UNKNOWN。HTTP 取消不等于远端副作用撤销，靠回执/状态查询恢复。
3. **统一补丁物化契约**：共享锚定和 overlay 规则；LLM dry-run 的早期反馈与 Web 最终验证一致。独立 fixtures 验证共享实现，避免重复错误。
4. **明确批次和依赖**：只并行独立读操作；有状态的 submit/review/memory 按作用域约束；依赖返回 patchId 的编译在后续阶段启动。区分“工具希望结束”与“全局停止”，不要简单改 every→some 后忽略在途结果和回执配对。
5. **明确验证信号**：passed 需要成功的编译状态、可信日志/产物证据与匹配的候选身份；失败/未知用结构化结果表示。对相同 snapshot/候选 hash 的重复验证提供合适的去重或已存在结果查询。

### 用评测决定策略改动

- 将 prompt 中的绝对修复配方改为依据源码和用户约束选择的建议；用反例验证，不继续堆特定错误的规则。
- 对合理的写作辅助，区分“基于作者给定材料起草”与“凭空编造结果/引用”。该产品边界需要负责人定稿；本方案暂将前者列为应支持能力。
- 对强制 todo-first、每批 3 工具、结果 4096 字节上界、历史 800 字符分页分别做小范围消融，测任务完成和成本。不要为了 token 更少让任务更容易失败。
- 大结果保留紧凑而完整的结构化状态（错误类别、目标 ID、计数、分页指针），精确正文按需读回；不要只剩一个无语义的归档占位符。
- 作者历史无限积累时，考虑“当前有效约束视图 + 原文索引 + 明确替代关系”；保留原文证据，先做覆盖早期要求/撤回/纠正的回归再优化。

不优先增加复杂 planner、多 agent 执行器、更多记忆层或更大模型。当前已有单 agent 闭环，先证明现有接口和状态语义可靠，再看失败证据是否支持架构升级。

## 11. token 与中断恢复

把总预算 B 分为建议比例：60% 真实 Copilot 运行、15% 争议复测、10% 模拟用户、5% 语义 judge、10% 预留。初期不用模拟器时，将该部分保留；比例不是要求花满。数据集生成优先程序模板，摘要等内部调用计入 Copilot 成本。

- runner 设置全局、每用例、每会话和每次模型调用预算；以实际 token 累计为主，开始下一调用前预留最坏允许开销。不能等 API 返回 usage 才第一次发现已超预算。
- 当前按模型回合数量/时间限流，不等于 token 总预算。建议新增可注入预算账本，覆盖主模型、摘要和其他模型服务；异常结束时记录 usage 是否完整。
- 先 L0，再跑 12 个小用例，每例一次；只对失败/争议重复。扩大后对变更使用同案例配对运行，固定模型/协议/参数，必要时重复 2–3 次并报告随机波动。
- 不假定 temperature 或 seed 能保证确定性。当前代码主服务使用 temperature=0.7，协议实际发送参数有差异，日志需记录最终有效请求。
- 每个模型/工具事件及每个用例结束后增量落盘；使用 `pending/running/completed/failed/interrupted` 状态。重启跳过已完成且配置 hash 相同的运行。
- 收到可能有副作用但没有回执的中断，先查询隔离后端状态；诊断式续跑与全新独立复测分开标记，不能把两次 run 拼成一次“成功”。

## 12. 执行顺序与交付物

| 阶段 | 最小工作 | 完成标准 |
|---|---|---|
| A：确认契约 | 定义状态/评分、搭严格 fake、12 个契约族，先聚焦 P0 | 核心失败能不靠在线模型稳定复现，测试本身有正负对照 |
| B：建立基线 | 12 个固定开发任务，隔离 Web/Mongo/编译依赖，接真实模型 | 每题有可独立判定结果、完整成本和轨迹；尚不要求全部通过 |
| C：修复闭环 | 每次一个机制，先复现再改 | 目标契约通过；相关固定任务无新硬失败；记录取舍 |
| D：扩大覆盖 | 36 场景、脚本多轮、少量受限模拟 | 冻结留出、报告分类型结果和不确定性 |
| E：持续回归 | 把代表性失败冻结为小 sentinel 集 | 后续 harness 变更先跑零模型测试，再用有限 token 检查 sentinel |

未来执行器建议放独立新目录，例如 `services/llm/harness-checks/`，不要读取或复用旧 `eval/`。此处仅规划，尚未创建。产出说明持续放 `doc/` 的 Markdown；未来大型机器轨迹可放独立 artifacts 目录，Markdown 记录索引、hash、结论和下一步。

每次暂停前，文档必须有“已完成 / 最新证据 / 待验证 / 下一条可执行动作”。这样即使 token 中途停止，也可以从最小失败或下一个场景继续。

本轮已完成代码梳理和 8 个离线补丁函数探针；没有运行完整 benchmark。下一步最有价值的具体动作：建立 C01/C02/C04/C05/C06 的最小契约测试，先验证身份、快照、终态、取消和停止语义，再用真实模型建立 12 题基线。
