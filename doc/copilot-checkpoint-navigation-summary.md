# Copilot 从 checkpoint 读取归档时产生无效动作的问题总结

本文总结 Overleaf Copilot 在上下文压缩后读取历史证据时出现的无效导航问题，包括问题背景、形成原因、修复前行为、探索过的方案、实验结果及最终实现。结论依据 2026-09-09 完成的合成 L1 单因素实验和生产路径回归；没有读取 Git 历史、其他分支或旧评测目录。

## 1. 背景

Copilot 的长会话不会把全部历史永久放进模型输入。上下文达到容量或经济阈值，或者用户手动发起压缩时，系统会把较旧的消息前缀替换成结构化 `PAPER_CHECKPOINT`，保留近期完整消息组。

原始历史并没有被删除，仍持久化在 MongoDB 中。checkpoint 保存作者要求、工具调用账本、补丁与编译状态等结构化信息。模型如果需要被压缩历史中的精确原文，应调用 `read_context_history` 重新读取原始消息。

这对 LaTeX 编辑尤其重要。例如，一个已经不在当前项目中的 `prior-decision.tex` 曾记录最终章节标题。checkpoint 可以告诉模型该文件以前被读取过以及工具结果位于哪条历史消息，但不能把旧文件内容直接当作当前源码使用。模型需要读回历史证据，再读取当前源码，最后提交候选补丁。

## 2. 问题是什么

修复前，checkpoint 的 `toolLedger` 已经包含工具名、调用参数和结果位置：

```json
{
  "name": "read_file",
  "arguments": { "path": "prior-decision.tex" },
  "resultMessage": 2
}
```

`read_context_history` 却只接受绝对消息编号：

```text
read_context_history(message=2, offset=0)
```

模型本应先在 checkpoint 中找到与目标文件匹配的账本项，再用 `resultMessage` 直接读取。但是实际运行中，模型经常从消息 0 开始顺序浏览：

```text
message 0, offset 0
message 0, offset 800
message 0, offset 1600
message 1, offset 0
message 2, offset 0
message 2, offset 800
message 2, offset 1600
```

其中，读取目标消息 2 的后续页面是必要动作；读取消息 0 和 1 则与当前任务无关。L1-27 和 L1-28 曾各产生 7 次历史读取，尽管 checkpoint 已经提供了 `resultMessage=2`。

这个问题没有直接证明 checkpoint 丢失信息。真实模型请求审计显示定位信息确实进入了模型上下文。问题在于系统把一个确定性的索引查询交给了模型：模型必须理解嵌套 checkpoint、识别正确工具账本项、提取消息编号并规划分页。模型可能忽略定位字段、采取保守的顺序扫描，或者重复确认已经存在的信息。

## 3. 为什么会产生无效动作

主要原因有四个。

第一，任务使用的是文件名，读取工具使用的是消息编号。模型需要完成一次本可由代码执行的映射：

```text
用户需要 prior-decision.tex
→ 在 toolLedger 找到 arguments.path 相同的条目
→ 读取 resultMessage
→ 再调用 history 工具
```

第二，checkpoint 信息密度较高。`toolLedger` 与作者要求、补丁、验证记录和解释规则一起序列化。即使定位字段存在，它也未必成为模型规划时最显眼的信息。

第三，模型有不确定性。相同生产描述在重复实验中，有时直接读取目标消息，有时从消息 0 浏览。说明提示本身不能稳定控制导航策略。

第四，历史证据需要兼顾正确性。简单地默认选择最近一次同名文件读取可能取错版本；自动把全部历史正文放回模型上下文又会抵消压缩收益。因此旧接口选择了安全但对模型不够友好的绝对消息编号。

## 4. 修复前的风险

无效读取会带来以下风险：

- 增加模型往返、输入 token、延迟和费用。
- 占用固定的 agent 步数，使编辑、编译或错误恢复更容易撞到步数上限。
- 把无关或已经撤销的旧讨论重新带入上下文，增加决策混淆。
- 重新扩大已经压缩过的模型输入，削弱 checkpoint 的容量收益。
- 增加工具参数生成次数，从而扩大格式错误等随机故障的暴露面。

本轮还观察到一个独立问题：模型在完成正确的历史导航后，生成了含非法 LaTeX 反斜杠转义的 `todo_write` JSON。严格解析失败使整轮任务终止。它不是归档定位错误，也没有在本次修复中处理，但说明不必要的额外步骤会增加任务暴露于其他故障的机会。

## 5. 考虑过的解决方案

### 5.1 强化工具描述

第一版方案只修改 `read_context_history` 的描述，明确要求：

- 优先根据 `PAPER_CHECKPOINT.toolLedger.resultMessage` 直达目标；
- 不要从消息 0 顺序扫描；
- 只在目标证据尚未出现时继续分页；
- 只有定位缺失或任务确实需要时才浏览其他消息。

优点是生产改动很小，不改变 checkpoint 和工具返回格式。缺点是仍然要求模型完成文件名到消息编号的查表。

9 对、18 会话实验中，无关历史读取从 19 次降到 0，总调用从 72 降到 61，输入 token 从 737,086 降到 598,129。但处理组只有 8/9 完成，控制组为 9/9。唯一失败发生在导航完成后的非法工具参数 JSON。由于预注册采用条件要求处理组全部完成，这个长描述没有进入生产。

### 5.2 只增加一句简短提示

为了排除长描述干扰模型规划，又测试了仅追加一句“根据匹配账本项的 `resultMessage` 直达”的版本。

3 对、6 会话中双方都完成任务，但处理组表现更差：模型调用从 16 增加到 20，输入 token 从 148,320 增加到 190,308，无关读取从 0 增加到 1。说明提示词效果有明显运行波动，简短提示也不能稳定降低成本，因此没有采用。

### 5.3 在 checkpoint 顶部增加显眼索引

这个方案会额外生成一个“文件路径 → 消息编号”的顶层索引，让定位信息比嵌套的 `toolLedger` 更容易看到。

它比原结构醒目，但仍要求模型读取索引、选择编号、再构造工具调用。它还会复制 checkpoint 中已有信息，增加 checkpoint 大小和一致性维护成本。由于前两轮已经显示“更明显的编号提示”不稳定，本轮没有优先实施。

### 5.4 自动将历史原文回填到模型输入

当 checkpoint 指向旧证据时，后端可以自动恢复相关正文并注入下一次模型请求。

这种方式可以减少显式工具调用，但后端必须猜测哪些证据与当前任务相关；自动加入错误版本或无关历史会增加输入成本和语义风险，也会模糊“历史证据”和“当前源码”的边界。它与上下文压缩降低输入量的目标冲突，因此没有采用。

### 5.5 增加语义检索或独立检索模型

可以为历史消息建立向量索引，按用户请求检索相关证据，或者增加一个模型负责导航。

这会引入召回率、索引一致性、额外模型成本和更复杂的评测问题。当前问题已有明确的文件路径，而历史工具账本本身就是可靠索引，没有必要为确定性查表引入概率检索，因此没有采用。

### 5.6 让历史读取工具支持文件名

最终方案是扩展现有 `read_context_history`：除了 `message`，还允许模型传入精确 `path` 和可选 `snapshotId`。

```text
read_context_history(path="prior-decision.tex", offset=0)
```

后端在当前会话的持久化 `read_file` / `read_file_fragment` 回执中完成文件名到消息编号的映射，然后复用原来的历史分页读取。这样模型只需表达“我要这个文件以前的证据”，确定性查表由代码执行。

## 6. 最终采用方案的行为

当前实现遵循以下规则：

1. 唯一匹配时，定位到对应绝对消息，并复用原有 800 字符串单位分页。
2. 多个匹配时，不默认选择最新版本，只返回候选消息、快照、哈希和读取范围。
3. 可以传 `snapshotId` 缩小候选范围；仍有歧义时继续返回候选。
4. 没有匹配时返回 `not_found`。
5. 原来的 `message` 入口完全保留，用于非文件型工具结果和已经知道消息编号的场景。
6. 读取到的仍是历史证据，不是当前源码；编辑前仍须读取当前项目文件。
7. 不自动注入历史正文，不新增检索模型，不改变摘要策略、页大小、工具预算或 agent 步数。

这种设计把系统边界放在更合适的位置：模型负责表达语义目标，即“需要哪个文件的历史证据”；代码负责完成稳定、可验证的索引解析。

## 7. 单因素实验结果

最终 A/D 实验覆盖三种布局：短证据位于消息 2、长证据位于消息 2、长证据位于消息 6，每种布局两对，共 12 个会话。配对任务、源码、项目标识、确定性 checkpoint、模型和预算一致；处理组只增加文件名入口。

| 指标 | A：原消息编号接口 | D：文件名入口 |
|---|---:|---:|
| 核心任务完成 | 6/6 | 6/6 |
| 目标原文恢复 | 6/6 | 6/6 |
| 无关历史读取 | 12 | 0 |
| 必要目标分页 | 14 | 14 |
| 全部历史读取 | 26 | 14 |
| 模型调用 | 45 | 37 |
| 输入 token | 455,031 | 357,219 |
| 输出 token | 16,264 | 12,670 |
| 总 token | 471,295 | 369,889 |

在这组开发样本中，总调用减少 17.8%，输入 token 减少 21.5%。必要目标分页数量完全相同，说明节省来自消除无关导航，而不是跳过证据。处理组每题都实际使用了 `path`，不是只改变 schema 而模型没有采用。

效果不是逐题单调的：6 对中有 3 对调用减少、2 对持平、1 对增加。因此能支持的结论是“这组任务的总体无效读取和成本下降”，不能承诺每次调用都更少，也不能从小样本推断线上平均成功率。

## 8. 生产接入和验证

文件名定位实现位于：

- `services/llm/app/agent/context/history-source-lookup.ts`
- `services/llm/app/services/copilot.service.ts`

确定性测试覆盖唯一位置、offset 保持、重复版本及分页歧义、快照筛选、归档完整回执恢复、缺失和失败回执、非法参数组合。

接入后完成了以下验证：

- L0 测试 87/87 通过；
- TypeScript 检查通过；
- 扩展 36 题全部预检通过；
- 生产路径 L1-25、L1-27、L1-29、L1-36 回归 4/4 通过。

其中，L1-25 验证真实手动压缩后按文件名读取短证据；L1-27 验证按文件名连续读取长证据三页；L1-29 验证非文件型大回执仍可使用旧消息编号入口；L1-36 验证近窗口约束、更正和 CRLF 保持。

## 9. 结论与剩余限制

最终没有继续堆叠提示词，而是选择了一个小范围的工具接口改进：把文件名到历史消息编号的确定性映射从模型侧移到后端。

这个方案解决了本轮观察到的主要无效导航，但没有消除所有模型无效动作。仍有以下限制：

- 同一路径存在多个历史版本时，模型还需要根据快照或候选元数据选择一次。
- 模型仍可以主动使用旧 `message` 入口浏览其他历史，系统没有强制禁止。
- 后端目前扫描当前会话历史并恢复匹配回执，大型日志下的数据库延迟尚未专项测量。
- 单因素实验是合成开发集，不能直接代表线上成功率或平均成本。
- 非法工具参数 JSON 导致当前轮次中止的问题仍未修复，应作为独立 harness 问题处理，不能与导航方案混在一次实验中。
