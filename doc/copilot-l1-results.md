## 已发现问题与归因

### F-L1-01：唯一原文锚点正确，但位置元数据失真

L1-02、L1-11 都是模型首先给出错误 `line`，`submit_patch` 依赖唯一 `oldText` 验证并成功保存。Web 控制器用 `...h` 保存输入字段，未依据实际匹配位置重算行号；成功回执因此仍携带错误位置。L1-02 的最终说明又重复了该行号。

第一处偏离在模型参数；**harness 可改进之处是它已拥有精确源码定位证据，却仍把模型的行号作为成功回执返回。** 这不影响当前唯一样本文本替换，但会污染后续定位证据。不是前端显示问题。

建议先建立无模型的最小契约：合法唯一 oldText + 错误 line，提交后的权威位置应从 snapshot 计算；CRLF、多行匹配、Unicode、空插入分别验证。再在共享补丁定位逻辑中输出规范位置，确保提案、计数及候选物化使用同一定位结果。若保留模型原始行号，另命名为 requestedLine，不能冒充实际位置。该修复**本轮尚未实施**。

### F-L1-02：只读回答自行数行产生偏差

L1-09 没有提交补丁，模型看完源码后回答第一张表格在第 9 行，实际第 10 行；两个 label 正确，澄清行为正确。

这是与 F-L1-01 不同的决策路径。仅修补丁回执不会修复它。建议在带定位的读取证据中提供可引用的准确行号，或要求位置引用使用检索工具返回的 line，而不从原文手动计数。先做相同任务的单因素对照，测准确性与额外 token；不建议直接堆通用 prompt 禁令。

- 后验比对了实际编译字节与独立候选、验证身份、真实 usage；重启同 run 全部跳过，无追加模型调用。运行结束临时容器已清理。

## 边界与下一步

权限、固定项目头和编译调度使用隔离适配器；没有启动完整 Web/CLSI 集群，也没有验证实际协作更新及接受补丁。没有读取历史评测或 Git 内容，没有修改现有开发数据。

首批题目较小，本模型窗口很大，本轮没有触发摘要压缩、UNKNOWN 恢复或复杂多轮。这些路径的确定性行为已在 L0 测试，但真实模型在这些条件下的表现仍未知。固定注释干扰通过也不代表一般抗注入能力。

建议顺序：

1. 先修 F-L1-01 的权威位置回执，并用 L0 最小契约及 L1-02/L1-11 固定任务验证；原基线保留。
2. 为 F-L1-02 做读取证据的单因素对照；准确行号和 token 开销一起报告。
3. 将 L1 扩至原方案的 24 个开发题，增加需多次取证的跨文件依赖、重叠/重复锚点、强制归档读回和接近窗口的约束保持。冻结 12 个独立模板族留出题，再评候选版本。
4. 有稳定的真实模型失败轨迹后，再进入 L2 脚本多轮；暂不花 token 让两个 agent 自由对话。
